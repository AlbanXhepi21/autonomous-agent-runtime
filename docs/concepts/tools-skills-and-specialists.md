# Tools, skills, and specialists

This inventory is generated by reading the live registries and security mappings, not
from documentation: [`backend/app/composition/providers/tools.py`](../../backend/app/composition/providers/tools.py)
(tool registration), [`backend/app/security/permissions.py`](../../backend/app/security/permissions.py)
(capability mapping), [`backend/app/security/risk.py`](../../backend/app/security/risk.py)
(risk classification), and [`backend/app/security/authorization.py`](../../backend/app/security/authorization.py)
(approval gating). See [agent-runtime.md](../architecture/agent-runtime.md) for how these
mechanisms fit into the decision loop.

## How to read "Risk" and "Approval"

Two independent things determine whether a tool call executes immediately, waits for a
human, or is refused outright:

1. **Four capabilities always require human approval, in every environment**, because
   they're gated ahead of everything else: `FILESYSTEM_WRITE` (`write_file`),
   `COMMAND_EXECUTE` (`run_command`), `PYTHON_EXECUTE` (`python_exec`), and
   `ARTIFACT_CREATE` (`register_artifact`). For these, "Risk" in the table below doesn't
   change the outcome — approval is required regardless of the value `RiskClassifier`
   would otherwise compute.
2. **Everything else is decided by risk level**, which itself depends on
   `SECURITY_ENVIRONMENT` (see [configuration.md](../getting-started/configuration.md)).
   Risk levels shown below are for a **non-production** environment (`unknown`,
   `development`, or `staging` — the classifier only special-cases the literal value
   `production`).

**A single environment setting changes almost everything below.** When
`SECURITY_ENVIRONMENT=production`, `RiskClassifier` treats *every* action as targeting a
"production-like resource" before it even looks at the tool's capability — this is
checked first, unconditionally. The practical effect: every read-only and analytics tool
that would otherwise auto-allow at LOW or MEDIUM risk instead becomes CRITICAL and is
**denied outright** in production, while the four already-gated tools continue to require
approval exactly as before (their gate never consulted the risk table to begin with). This
is documented in full, with the reasoning, in
[limitations.md](../reference/limitations.md#the-production-security-environment-is-a-near-total-kill-switch-not-a-tightening).

### `web_search`: an interface with no provider

`WebSearchTool` (`backend/app/tools/web_search.py`) is a real class with a real argument
schema and a real capability mapping (`WEB_SEARCH`), but:

- Its `execute()` method unconditionally raises `NotImplementedError("A web search
  provider has not been configured yet.")` — it has never done anything.
- It is **never instantiated or registered** in `get_tool_registry()`
  (`backend/app/composition/providers/tools.py`) — grepping the entire `composition/`
  tree confirms no reference to `WebSearchTool` exists there.

The result is that `web_search` is not merely a degraded feature — it is unreachable by
the running agent at all. The `research` specialist, which would be the natural consumer
of a working web search, has an empty `allowed_tools` list as a direct consequence (see
below): it can only reason from context and its own skill instructions.

## Skills

Skills are Markdown instruction bundles, not executable code — a `load_skill` action
loads a skill's text into the run's context; nothing about a skill's content is validated
or interpreted beyond its metadata shape. Selection is entirely the model's choice: the
registry offers every skill not already loaded this run, with no request-type-based
recommendation logic.

| Name | Purpose | Resource path | Version | Tags |
|---|---|---|---|---|
| `data_analysis` | Turn a business question into bounded, reproducible evidence | `backend/app/resources/skills/data_analysis/` | 1.3.0 | data, analysis, evidence, statistics, reproducibility |
| `executive_reporting` | Produce concise, evidence-backed analytical reports and artifacts | `backend/app/resources/skills/executive_reporting/` | 1.0.0 | reporting, executive, evidence |
| `research` | Plan evidence gathering, assess source quality, produce qualified conclusions | `backend/app/resources/skills/research/` | 1.1.0 | research, verification, evidence, source-evaluation, uncertainty |
| `software_engineering` | Inspect, debug, change, and verify software with focused repository operations | `backend/app/resources/skills/software_engineering/` | 1.1.0 | software, debugging, testing, repository, verification |

Each skill's `metadata.json` also declares `recommended_tools` — a hint, not an
enforcement mechanism (nothing checks that a loaded skill's recommended tools are
actually available or used):

- `data_analysis`: `calculator`, `list_tables`, `describe_table`, `get_table_relationships`, `search_schema`, `query_database`, `create_chart`, `analyze_dataset`
- `executive_reporting`: `query_database`, `analyze_dataset`, `generate_report`
- `research`: *(none)*
- `software_engineering`: `get_repository_tree`, `search_files`, `read_file`, `write_file`, `run_command`

**Selection behavior**: purely the model's choice via the `load_skill` action's `enum` of
available names. **Constraints**: a specialist's own registry is restricted to that
specialist's `allowed_skills` (see below) — this is a structural allow-list applied at
delegation time, not a runtime filter on top of a shared registry.

## Specialists

A specialist is a sub-agent invoked via `delegate`/`delegate_parallel`, discovered from
`backend/app/resources/specialists/*/metadata.json` + `AGENT.md`. Selection is purely the
model's choice of `agent_name`, exposed as a flat enum with no registry-side
recommendation — the project's own README states this is deliberate: *"delegation is
always an explicit, model-selected, single-level choice"* (recursive delegation and
automatic routing are both intentionally absent).

| Name | Purpose | Resource path | Allowed tools | Allowed skills | `max_iterations` override |
|---|---|---|---|---|---|
| `data_analyst` | Structured quantitative analysis and interpretation | `backend/app/resources/specialists/data_analyst/` | `calculator`, `list_tables`, `describe_table`, `get_table_relationships`, `search_schema`, `query_database`, `analyze_dataset`, `create_chart`, `generate_report`, `list_metrics`, `describe_metric` (11 tools) | `data_analysis`, `executive_reporting` | 8 |
| `research` | Investigate external factual questions and collect evidence | `backend/app/resources/specialists/research/` | *(none)* | `research` | 6 |
| `software_engineer` | Analyze software architecture, debugging, and technical problems | `backend/app/resources/specialists/software_engineer/` | `calculator`, `list_files`, `read_file`, `write_file`, `run_command`, `python_exec`, `get_repository_tree`, `search_files`, `get_changed_files`, `git_inspect`, `register_artifact` (11 tools) | `software_engineering` | 8 |

**Constraints, all structurally enforced, not conventions:**

- A child runner's `ToolRegistry`/`SkillRegistry` are rebuilt containing *only* the
  granted names — an ungranted tool doesn't exist in the child's registry, so calling it
  fails the same way a typo would, rather than being filtered at call time.
- A specialist runs at `agent_depth=1` with delegation disabled on the child runner —
  combined with the default `max_agent_depth=1`, a specialist cannot itself delegate
  further under default configuration.
- The four approval-gated capabilities still apply to a specialist's tool calls — a
  specialist cannot use its grants to bypass human approval for `write_file`,
  `run_command`, `python_exec`, or `register_artifact`.
- `research`'s empty `allowed_tools` means it currently has no way to gather evidence
  beyond what's already in its context — a direct consequence of `web_search` being
  unimplemented (see above).

See [agent-runtime.md](../architecture/agent-runtime.md#skills-and-specialists) for the
full delegation mechanism, including how a child's result is folded back into the parent
run.
